# V1 功能模块与分支开发指导

日期: 2026-05-28
基线: V1 UI 原型验收后
适用范围: 从 UI 壳进入可用 MVP 的功能开发阶段

## 1. 指导目标

本文用于把 V1 UI 原型后的开发工作拆成可独立推进、可验收、可回滚的功能分支。

拆分原则不是按页面拆，而是按风险边界、依赖顺序和数据所有权拆。后续开发应避免把数据层、编辑器、AI、连续性复盘混在同一个分支里推进。

## 2. 总体开发原则

- 主分支只接收已验收的功能分支，不直接堆功能。
- 每个分支必须有明确目标、范围边界、验收标准和回滚边界。
- 分支内可以做必要的小重构，但不得顺手重写无关模块。
- 数据写入路径优先稳定，再做依赖它的编辑器、AI 和复盘能力。
- AI 生成结果不得自动覆盖正文或自动写入作品事实库，必须经过用户确认。
- UI 原型已验收的布局、主题和交互壳不得在功能分支中被大面积推翻。

## 3. 推荐分支总览

| 顺序 | 分支名 | 模块 | 主要目标 |
| --- | --- | --- | --- |
| 1 | `v1-data-store` | 数据与项目仓储层 | 收敛数据读写边界，为后续模块提供稳定基础 |
| 2 | `v1-editor-core` | 写作编辑器核心 | 提升章节正文编辑、保存、选区和长文本体验 |
| 3 | `v1-context-relations` | 人物 / 资料 / 章节关系系统 | 让人物和资料真正服务当前章节上下文 |
| 4 | `v1-ai-context` | AI 上下文与请求层 | 从 mock 输出升级到可接真实模型的上下文系统 |
| 5 | `v1-continuity-review` | 章节复盘与连续性系统 | 写完章节后沉淀摘要、人物状态、设定变更和伏笔 |
| 6 | `v1-export-publish-ready` | 导出与发布准备 | 稳定导出单章和全书，预留平台格式 |

推荐依赖关系:

```text
v1-data-store
  ↓
v1-editor-core        v1-context-relations
  ↓                         ↓
v1-ai-context
  ↓
v1-continuity-review

v1-export-publish-ready 可在 v1-data-store 后并行推进
```

## 4. 分支一: 数据与项目仓储层

分支名: `v1-data-store`

### 4.1 目标

把当前散落在 UI 组件中的 `onPatchState` 写入收敛为稳定的数据访问层，让 UI 不再直接关心具体存储实现。

### 4.2 范围

- 设计项目、卷、章节、人物、资料、章节关联、AI 请求的仓储接口。
- 保留 localStorage 作为第一版适配器。
- 增加数据版本号和迁移预留。
- 增加项目数据导入 / 导出备份。
- 明确删除级联规则，例如删除章节时清理人物关联、资料关联和 AI 请求。
- 为后续 IndexedDB、本地文件或服务端 API 迁移保留接口。

### 4.3 不做

- 不接真实后端。
- 不做登录注册。
- 不改写 UI 视觉框架。
- 不引入复杂数据库同步策略。

### 4.4 验收标准

- 刷新页面后作品、章节、人物、资料、关联关系不丢失。
- UI 层新增和修改数据时通过数据服务完成，不直接依赖 localStorage。
- 项目数据可以导出为备份文件。
- 备份文件可以导入并恢复核心数据。
- 删除项目、章节、人物、资料时，相关引用不会留下明显脏数据。

### 4.5 回滚边界

该分支只改变数据访问方式和必要调用点。若出现问题，应能回滚到当前 localStorage 状态管理原型，不影响 UI 基线。

## 5. 分支二: 写作编辑器核心

分支名: `v1-editor-core`

### 5.1 目标

把章节正文编辑从 `textarea` 原型升级为可长期演进的写作组件，并为 AI 选区处理提供基础能力。

### 5.2 范围

- 封装独立章节编辑器组件。
- 明确是否引入 CodeMirror、TipTap、Monaco，或继续自研轻量编辑器。
- 支持自动保存状态和手动保存。
- 稳定字数统计。
- 支持基础撤销 / 重做。
- 支持搜索 / 替换入口。
- 支持选中文本捕获。
- 支持在光标处插入 AI 输出。
- 支持替换选中文本的基础接口，但不默认自动替换。
- 验证长文本输入性能。

### 5.3 不做

- 不做复杂富文本排版。
- 不做图片、表格、批注。
- 不接真实 AI。
- 不做多人协同。
- 不重构人物、资料和 AI 业务逻辑。

### 5.4 验收标准

- 用户可以连续输入长文本，输入体验不卡顿。
- 字数统计稳定并与正文内容一致。
- 自动保存状态清晰，不打断写作。
- 手动保存入口可用。
- 可以获得当前选中文本，供后续 AI 润色 / 改写使用。
- 可以把外部文本插入正文或替换选区。
- 不破坏当前工作台三栏布局。

### 5.5 回滚边界

该分支只替换章节正文编辑能力。若编辑器方案失败，应能回退到原 textarea 组件。

## 6. 分支三: 人物 / 资料 / 章节关系系统

分支名: `v1-context-relations`

### 6.1 目标

让人物和资料不再只是孤立表单，而是成为当前章节上下文的一部分，为 AI 和连续性系统提供可靠输入。

### 6.2 范围

- 完善章节关联人物。
- 完善章节关联资料。
- 支持人物出场记录的基础展示。
- 支持资料引用记录的基础展示。
- 优化右侧上下文面板中的相关人物和相关资料。
- 明确人物、资料、章节之间的引用关系数据结构。
- 为 AI 上下文组装提供稳定的查询能力。

### 6.3 不做

- 不做复杂知识图谱。
- 不做自动识别人物出场。
- 不做拆书素材库。
- 不做时间线和伏笔库完整功能。

### 6.4 验收标准

- 用户可以把人物关联到当前章节。
- 用户可以把资料关联到当前章节。
- 当前章节右侧上下文能稳定显示相关人物和资料。
- 切换章节后，上下文能跟随变化。
- AI 上下文层可以读取当前章节的相关人物和资料。

### 6.5 回滚边界

该分支只增强关联关系和上下文展示，不改变核心写作编辑器，不接真实 AI。

## 7. 分支四: AI 上下文与请求层

分支名: `v1-ai-context`

### 7.1 目标

从模拟 AI 输出升级到可接真实模型的上下文组装和请求系统，同时避免前端直接暴露 API Key。

### 7.2 范围

- 统一 AI 任务类型: 续写、润色、总结、改写。
- 预留 AI 任务类型: 检查、复盘。
- 设计上下文组装规则。
- 上下文至少包含作品信息、章节标题、章节目标、正文片段、章节摘要、相关人物、相关资料。
- 设计 AI 请求记录结构。
- 支持请求中、成功、失败状态。
- 支持输出复制、插入正文、替换选区的策略接口。
- 保留 mock provider。
- 设计服务端代理接口，后续真实模型通过代理调用。

### 7.3 不做

- 不在前端直接保存或暴露真实 API Key。
- 不让 AI 输出自动覆盖正文。
- 不让 AI 自动修改人物库、资料库或作品事实。
- 不在本分支实现完整章节复盘流程。

### 7.4 验收标准

- AI 面板可以根据任务类型组装不同上下文。
- 每次 AI 请求有基础记录，包含任务、输入快照、输出、状态和时间。
- mock provider 能走完整请求状态流程。
- AI 输出默认只进入结果区。
- 用户确认后，AI 输出才进入正文。
- 请求失败时有可读错误状态。

### 7.5 回滚边界

该分支只替换 AI 请求和上下文组装层。若真实 provider 未就绪，仍可回退到 mock provider。

## 8. 分支五: 章节复盘与连续性系统

分支名: `v1-continuity-review`

### 8.1 目标

建立 Webnovel IDE 的核心差异化能力: 作者写完一章后，系统辅助沉淀摘要、人物状态变化、设定变更、伏笔和冲突。

### 8.2 范围

- 增加“完成本章”或“章节复盘”入口。
- 设计章节复盘结果结构。
- 支持生成本章摘要。
- 支持提取人物状态变化。
- 支持提取新增设定或设定变更。
- 支持提取伏笔、未解决问题和冲突。
- 支持用户逐项编辑、确认、忽略。
- 确认后再写入人物库、资料库或后续连续性记录。
- 保留复盘记录，支持回看和基础撤销。

### 8.3 不做

- 不让 AI 自动写入事实库。
- 不做完整知识图谱可视化。
- 不做平台数据反馈。
- 不做团队审稿流程。

### 8.4 验收标准

- 作者可以在章节完成后触发复盘。
- 复盘结果可以编辑。
- 复盘结果必须经用户确认后才写入作品数据。
- 被确认的摘要、人物状态或设定变更能被后续章节上下文引用。
- 用户可以查看本章复盘记录。

### 8.5 回滚边界

该分支依赖数据层、上下文关系和 AI 上下文。若复盘体验未达标，应能关闭入口，不影响章节写作、人物资料维护和普通 AI 辅助。

## 9. 分支六: 导出与发布准备

分支名: `v1-export-publish-ready`

### 9.1 目标

让作者能稳定导出单章和全书文本，并为后续网文平台发布格式做准备。

### 9.2 范围

- 单章 TXT 导出。
- 单章 Markdown 导出。
- 全书 TXT 导出。
- 全书 Markdown 导出。
- 按卷和章节顺序组装内容。
- 导出预览。
- 文件命名规则。
- 平台格式预设预留，例如番茄、起点、七猫。

### 9.3 不做

- 不做自动发布平台。
- 不做平台账号登录。
- 不抓取平台数据。
- 不做复杂排版模板市场。

### 9.4 验收标准

- 单章导出包含章节标题和正文。
- 全书导出包含卷名、章节标题和正文。
- 章节顺序与工作台显示顺序一致。
- Markdown 格式可读。
- 导出空章节时有合理提示或占位处理。

### 9.5 回滚边界

该分支只影响导出流程和导出服务，不改变写作编辑器和 AI 系统。

## 10. 可合并为四个分支的简化方案

如果团队人力较少，也可以压缩为四个分支:

| 分支名 | 合并内容 |
| --- | --- |
| `v1-data-store` | 数据仓储、导入导出备份 |
| `v1-editor-core` | 写作编辑器、保存、选区、插入 |
| `v1-ai-context-and-relations` | 章节关系、上下文面板、AI 请求层 |
| `v1-continuity-and-export` | 章节复盘、连续性记录、发布导出 |

不推荐继续压缩。数据、编辑器和 AI 至少应保持独立，否则后续排查问题和回滚会非常困难。

## 11. 每个分支的交付模板

每个功能分支合并前至少补齐以下内容:

```text
分支名:
目标:
本次实现:
未实现但预留:
数据结构变化:
用户可见变化:
验收步骤:
回滚方式:
风险:
```

建议在 `docs/release` 下为每个分支补一份阶段总结，例如:

```text
docs/release/2026-xx-xx-v1-data-store-summary.md
```

## 12. 当前不建议启动的分支

以下能力暂不建议在当前阶段启动:

- 登录注册。
- 支付和订阅。
- 团队协作。
- 权限系统。
- 自动发布平台。
- 平台数据自动抓取。
- 大规模知识图谱。
- 插件市场。
- 模板市场。

原因是这些能力依赖稳定的数据模型、编辑器和 AI 上下文系统。核心写作闭环跑通之前，过早引入会增加架构负担。

## 13. MVP 闭环完成定义

当以下能力全部可用时，可以认为 V1 MVP 的核心写作闭环完成:

- 用户可以创建作品。
- 用户可以创建卷和章节。
- 用户可以稳定撰写长文本。
- 正文可以自动保存并刷新后恢复。
- 用户可以维护人物和资料。
- 用户可以把人物和资料关联到章节。
- AI 可以基于当前章节上下文生成结果。
- AI 输出由用户确认后进入正文。
- 用户写完章节后可以触发复盘。
- 复盘结果经用户确认后沉淀回作品数据。
- 用户可以导出单章和全书文本。

这个闭环完成后，再考虑协作、商业化、平台发布和数据反馈。
