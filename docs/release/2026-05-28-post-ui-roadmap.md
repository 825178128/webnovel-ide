# V1 UI 后续开发任务

日期: 2026-05-28
基线分支: v1-development

## 1. 开发原则

UI 分支合并后，后续工作应拆分为独立功能分支。

原则:

- 不在主分支直接堆功能。
- 每个功能分支必须有清晰目标、验收标准和回滚边界。
- AI、数据、编辑器、复盘等模块分别推进，避免互相污染。
- 凡是超出 UI 壳的需求，需要进入独立功能设计文档。

## 2. 建议分支一: 数据持久化

建议分支名: `v1-data-persistence`

目标:

- 从单纯 localStorage 原型升级到更可控的数据层。
- 明确项目、卷、章节、人物、资料、AI 请求的读写边界。
- 为后续本地文件、IndexedDB 或服务端 API 迁移做准备。

任务:

- 设计数据仓储接口。
- 抽离当前 `onPatchState` 的写入路径。
- 增加导入 / 导出项目数据能力。
- 增加基础数据备份策略。

验收:

- 刷新后数据稳定。
- 项目数据可导出备份。
- UI 层不直接依赖具体存储实现。

## 3. 建议分支二: 编辑器核心

建议分支名: `v1-editor-core`

目标:

- 提升章节写作体验。
- 让编辑器从 textarea 原型升级为可长期演进的写作组件。

任务:

- 明确是否引入 CodeMirror、TipTap、Monaco 或继续自研轻量编辑器。
- 设计自动保存状态。
- 设计章节标题、正文、字数统计、快捷键。
- 增加撤销、搜索、替换、定位等写作辅助入口。

验收:

- 长文本输入不卡顿。
- 字数统计稳定。
- 自动保存状态清晰。
- 不破坏当前 UI 框架。

## 4. 建议分支三: AI 上下文系统

建议分支名: `v1-ai-context-shell`

目标:

- 从模拟输出转向可接真实模型的上下文组装层。
- 避免前端暴露 API Key。

任务:

- 设计服务端代理接口。
- 设计章节、人物、资料上下文组装规则。
- 设计 AI 请求日志和结果插入策略。
- 区分续写、总结、润色、检查、复盘等任务类型。

验收:

- 前端不直接携带密钥请求模型。
- AI 面板可展示请求中、成功、失败状态。
- AI 输出不会直接覆盖用户正文。

## 5. 建议分支四: 章节复盘与连续性

建议分支名: `v1-continuity-system`

目标:

- 建立网文 IDE 的核心差异化能力。
- 让章节写完后能自动沉淀摘要、角色状态、设定变更、伏笔和冲突。

任务:

- 设计章节完成后的复盘入口。
- 设计章节摘要、出场人物、设定引用、伏笔、冲突、情绪目标的数据结构。
- 设计连续性检查 UI。
- 设计人工确认流程，避免 AI 自动写入错误事实。

验收:

- 作者可以在写完章节后触发复盘。
- 复盘结果可编辑、可确认、可撤销。
- 后续章节能引用已确认事实。

## 6. 建议分支五: 资料库信息架构

建议分支名: `v1-knowledge-base-ia`

目标:

- 明确“设定 / 资料 / 素材 / 世界观”的产品命名和层级。
- 避免资料库成为孤立表单。

任务:

- 决定左侧显示名称。
- 区分世界设定、人物关系、地点组织、规则系统、素材摘录。
- 设计资料与章节、人物之间的引用关系。

验收:

- 用户知道资料库放什么。
- 资料能和章节写作产生关系。
- 不把拆书素材、世界观、写作备忘混成一团。

## 7. 当前不建议立即做

- 登录注册。
- 支付和订阅。
- 团队协作。
- 发布平台自动对接。
- 大规模复杂知识图谱。

原因:

这些能力依赖稳定的数据模型、编辑器和 AI 上下文系统，应在核心写作闭环跑通后再做。
